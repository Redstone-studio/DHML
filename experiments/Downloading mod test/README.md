# 实验项目使用说明

`experiments\Downloading mod test` 的使用手册。这是个**试验田**——用来试搜索/下载/动画/背景这些东西，不是正式项目。正式项目在 `D:\DHML-src` 根目录。

---

## 一、怎么跑起来

```powershell
cd "D:\DHML-src\experiments\Downloading mod test"
python main.py
```

依赖：`PyQt6` + `requests`（和根项目一致）。要求联网（Modrinth API）。

数据存在 `%APPDATA%\MosslightModTest\`：

| 文件 | 内容 |
|---|---|
| `setting.json` | 动画预设、速度、背景、卡片透明度、淡入开关 |
| （图标缓存在 `core/cache.py` 管的地方） | 下载过的模组图标，避免重复请求 |

嫌设置乱了想回到出厂状态：把 `setting.json` 删掉就行（下次启动会用默认值重新生成）。

## 二、界面结构

### 搜索页（主页面）

从上到下：

```
┌─ 筛选卡片 ────────────────────────────────┐
│ 搜索模组                    ← 标题，跟着标签页变   │
│ [搜模组] [搜光影] [搜资源包] [搜数据包] [搜整合包]  │  ← 类型标签（按钮）
│ [ 搜索框                                 ]  │
│ 版本: [全部▾]  加载器: [全部▾]  分类: [全部▾]     │
│ [🔍 搜索模组] [重置] [动效] [背景]   状态文字     │
└──────────────────────────────────────────┘
┌─ 结果列表（可滚动）──────────────────────────┐
│  卡片、卡片、卡片……                        │
└──────────────────────────────────────────┘
[加载条]  ← 请求进行中时出现在最下面
```

**几个要点：**

- **类型是标签页不是下拉框**。点一下会**直接重新搜索**（不用再点搜索按钮），同时标题和按钮文字会跟着变（"搜索光影"）。加载器那栏只对"模组"有意义，切到别的类型会自动禁用。
- **搜索框回车 = 点搜索按钮**。
- **重置**：清空关键词、把版本/分类/加载器/类型都归零，然后重新搜一次。
- **加载条**在滚动区**外面**，所以滚列表时它一直在。请求很快时会兜一个最短显示时间，免得一闪而过。

### 详情页

点任意一张卡片进来。结构：

```
[← 返回]
┌─ 模组信息卡（固定，不跟着滚）─────────────┐
│ 图标  Fabric API | fabric-api            │
│       标签 / 描述 / 下载量 / 上次更新       │
│       [转到 Modrinth] [转到 MC 百科] [复制名称] │
└────────────────────────────────────────┘
┌─ 版本列表（只有这块滚）───────────────────┐
│ ▸ Fabric 26w14a 预览版                   │  ← 点一下展开
│ ▸ Fabric 26.4-snapshot-1 预览版          │
│ ▸ Fabric 26.3                            │
│   ……（滚到底会自动加载下一批）              │
└────────────────────────────────────────┘
```

**「转到 MC 百科」是直达词条的**（不是搜索页），机制见下面「MC 百科直达」。

**几个要点：**

- **上面的信息卡是固定的**，只有下面的版本列表滚——往下翻的时候图标和按钮不会被滚走。
- **版本按"加载器 + 游戏版本 + 是否预览版"分组**。一个模组可能有 400 多个分组（Fabric API 就是），所以是分批加载的。
- 展开分组 → 里面是具体版本卡片，每张有「⬇ 下载」按钮。
- **下载流程**：确认框 → 选保存目录 → 下载 → 提示完成。

## 三、动效设置（工具栏「动效」按钮）

左边选风格，右边**实时预览**（三张示意卡片用当前设置演一遍），下面调速度。**改完立刻生效**，不用重启。

### 七档风格

| 档位 | 说明 |
|---|---|
| 左侧滑入 | 从左边滑进来，干脆利落 |
| 下方滑入 | 从下面升上来 |
| 左侧滑入（弹簧） | 弹簧式过冲后自己收住（阻尼正弦，一条连续曲线） |
| 仿 PCL2（克制） | 位移很短、收尾绵长（**这档是我瞎猜的**，和真 PCL 无关） |
| 左侧滑入（过冲 18%） | 过冲量可调，不是 Qt 那个写死的 10% |
| 下方滑入（弹性） | 来回弹几下才停 |
| **PCL 原味（拆两条 + 淡入）** | 按 PCL 的真实配方做的，**推荐先试这个** |

### PCL 原味那档特殊在哪

普通档位是"一条缓动曲线走完"。PCL 的做法是**三条并行**：

```
透明度   0 → 1        100ms
位移 A   +31% → 0     71% 时长，OutQuint    ← 快速把主要位移走完
位移 B   +69% → 0     全时长，带轻微过冲    ← 慢一点、结尾轻轻一顿
```

一条曲线要么结尾太硬（OutCubic），要么全程软绵绵（InOutCubic）；拆成两条才有"先快后慢 + 收尾一顿"的层次。实测合成轨迹：189ms 处过冲 +2.55px，250ms 走完 96%，350ms 精确归零。

### 速度档位

时长和错峰**一起缩放**（只放慢单张、不放慢错峰的话，卡片会变成一张张慢慢蹦）。

| 档位 | 单张时长 | 错峰 | 一批 12 张铺完 |
|---|---|---|---|
| 快 0.7× | 294ms | 66ms | 0.86s |
| 标准 1× | 420ms | 95ms | 1.20s |
| 慢 1.5× | 630ms | 142ms | 1.71s |
| 很慢 2.2× | 924ms | 209ms | 2.41s |
| 夸张 3.2× | 1344ms | 304ms | 3.45s |

觉得"太快看不清"就调这个——**多半不是单张滑得太快，而是错峰太小**（卡片几乎同时出现，眼睛来不及捕捉"依次滑入"的过程）。

## 四、背景设置（工具栏「背景」按钮）

改完**立刻生效**，不用重启。

### 背景图

任意图片，带「浏览…」。**优先级：有图片就用图片**，纯色只在没图片时生效——所以想用纯色要先把图片那栏清空。

五种铺法，命名对齐 Windows 的「选择适合度」：

| 选项 | 行为 |
|---|---|
| 填充 | 等比放大铺满，多出来的裁掉（留有黑边的反面） |
| 适应 | 等比缩放到整图可见，不够的地方留边 |
| 拉伸 | 直接拉满，比例会变形 |
| 居中 ← **默认** | 原图大小放中间，四周留边 |
| 跨区 | 横向铺满、纵向居中裁切 |

> Windows 的「平铺」**故意没做**。想加回来的话：`ui/widgets/appearance.py` 的 `MODES` 里补一行，再去 `background_canvas._draw_image` 加一个按行列贴图的分支（几行的事）。

### 压暗（0~200）

叠一层半透明黑色。**亮背景会把卡片和文字冲得看不清，这层能救回来**。图 + 压暗 90 左右最舒服。

### 卡片透明度（10~100%）

只改**卡片底色**的 alpha，**文字和图标不受影响**——所以是"背景透出来、字还是清楚的"，而不是整张卡片连字一起变淡。

实现上没走 `QGraphicsOpacityEffect`（那个会把文字一起弄糊），而是把卡片背景色换成 `rgba(35, 36, 40, α)`。三类卡片（搜索结果、版本分组、具体版本）都走 `ui/widgets/card_style.py` 这一个出口。

### 入场淡入

开关。**卡顿排查用的**——淡入要给每张卡片挂 `QGraphicsOpacityEffect`（渲染到离屏缓冲再合成），显卡弱/驱动不合的机器上会掉帧。觉得动画卡就先关它试试。

### 下载与访问（多线程）

一个总开关 + 一个线程数滑块：

- **开关关着**（默认）：线程数固定用默认值 **8**，滑块那一节**收起**（只有标题栏）。
- **开关打开**：滑块那一节**带动画展开**，线程数取滑块的值。
- 滑块范围 **1~32**，默认 8。改滑块会立刻落盘；**关掉开关不会丢失滑块上的数字**，下次打开还在，但**实际生效的是默认值 8**。

语义就一句话：**开关关 → 一律用默认值**。这个规则只在 `appearance.effective_threads()` 一处实现，别处都读它，所以不会出现"某个地方忘了判断开关"。

目前它作用在**图标下载的线程池**上（搜索页和详情页各一个池，都读同一个设置）。范围 8~16 一般最舒服——开太多会互相抢带宽，也容易被服务端限速。

> 这个"开关 + 可收起子项"的结构用的是 `ui/widgets/collapsible_section.py`（从版本分组那套高度动画抽出来的通用组件）。以后设置页里再要"打开才显示更多选项"，直接用它。

## 五、MC 百科直达（原理）

点「转到 MC 百科」会**直接打开对应词条**（如 Fabric API → `mcmod.cn/class/3124.html`），
不是搜索页。

### 为什么需要"解析"这一步

我们搜的是 **Modrinth**，用户想看的是 **MC 百科**，两边**没有任何共享 ID**，
名字也不完全一样（Modrinth 叫 "Fabric API"，百科词条叫 "FabricAPI"）。

**Modrinth 的接口帮不上忙**（实测）：

- `project.wiki_url` 指的是**项目自己的 wiki**（`fabricmc.net/wiki`、GitHub wiki 那种），不是百科
- 搜索接口的 hit 里连 `wiki_url` 字段都没有

**MC 百科的官方 API 也走不通**：`api.mcmod.cn` 一律返回 **403**，文档站也要权限，是私有的。

### PCL2 是怎么做的（供参考）

它**自带一个离线数据库**：`Resources/mcmod.buf` 是压缩过的 SQLite，
里面有 `WikiId` 字段 —— 也就是"Modrinth/CurseForge 项目 → 百科 class ID"的映射表
（`ModComp.cs` 就是在读写这个库，154KB）。

- 好处：不联网、100% 准、跳转零延迟
- 代价：这个库要跟着版本维护；而且格式是它自己的（protobuf + 压缩），我们没法直接复用

### 我们的做法：抓百科自己的搜索页

```
https://search.mcmod.cn/s?key=<名字>   →   从结果里挑最像的   →   /class/<数字>.html
```

### 匹配按**置信度分三档**（这是"不跳错词条"的关键）

一个名字在百科会撞上一堆相似的。搜 `Fabric API` 的实际结果：

```
[3124 ] FabricAPI                      ← 我们要的
[11464] [FFAPI] Forgified FabricAPI    ← Forge 移植版，另一个模组
[6246 ] [QSL] Quilt Standard Libraries
[3785 ] Cloth API
[6788 ] [QFAPI] Quilted FabricAPI
```

所以 `pick_best()` 返回的不是"最像的那个"，而是**带置信度的结果**：

| 档位 | 判定 | 界面行为 |
|---|---|---|
| `exact` | 归一化后**完全相同**（"Fabric API" ≡ "FabricAPI"） | **直接跳**，按钮写「转到 MC 百科」 |
| `strong` | 互相包含且**长度比 ≥ 0.6** | 按钮写「MC 百科（确认）」，点了**弹菜单让用户选** |
| `weak` | 只靠词重合度（Jaccard ≥ 0.55） | 同上，必须确认 |
| `None` | 都不满足 | 直接开搜索页 |

**长度比这个门槛是专门用来防"撞名"的**：查询 `fabricapi`(9) 对上
`fabricapilegacy`(15) 比例 0.6，算像；但对上 `forgifiedfabricapi`(18) 只有 0.50，
就判成"不是同一个东西"，**宁可返回 None 也不硬选**。

确认态弹的菜单长这样：

```
① 直接去词条：[FFAPI] Forgified FabricAPI
──────────
② 去百科搜索页，我自己挑
```

**拿不准宁可不跳**——跳错词条比让用户多点一下糟糕得多。

### 名称变体：为什么必须做

**百科词条标题是「[简称] 中文名 (English Name)」**，比如
`"模组说明 (ModMenu)"`、`"[OF] 高清修复 (OptiFine)"`、`"星光 (Starlight)"`。
而 Modrinth 给的是英文名，直接比是对不上的。

所以 `_variants()` 会把**括号里的英文名**和**去掉方括号简称的部分**都抠出来当变体比：

| | 不做变体 | 做了变体 |
|---|---|---|
| 命中率 | 5/14 | **12/14** |

（`Iris` 这种对不上是合理的：百科词条叫 `IrisShaders`，归一化后是 `irisshaders`，
查询 `iris` 只占 4/11 = 0.36，低于门槛 → 退回搜索页。）

### 两个坑

1. **百科会限速**。连续快速请求时它会**交替**返回正常页和"没有结果"的页，
   而且 **HTTP 仍然是 200** —— 只看状态码发现不了，表现为"有时能匹配有时匹配不上"
   （实测连续 10 次里 5 次是空的）。
   对策：请求之间强制留 0.5s 间隔，页面里找不到结果块就等 0.7s 重试（最多 3 次）。
2. **正则里的捕获组会坑 `re.findall`**。结果块的正则如果写成 `(<div class="result-item">)(.*?)`，
   `findall` 只会返回第 1 个分组（而且第一个结果块还会被吃掉）。
   要用非捕获组 `(?:...)`。

### 界面行为

按钮有**三种状态**，文字就说明白了会跳到哪：

| 按钮文字 | 什么时候 | 点下去 |
|---|---|---|
| **转到 MC 百科** | 名字精确命中 | 直接进词条 |
| **MC 百科（确认）** | 只做到"像"（strong/weak） | 弹菜单：去词条 / 去搜索页 |
| **MC 百科（搜索）** | 没解析到 / 还没解析完 | 进搜索结果页 |

- 进详情页**立刻**就是可点的状态（先用搜索页兜底），不用等解析
- 后台线程解析（`ui/workers/mcmod_worker.py`），结果回来就升级按钮
- 悬停提示里**写清词条名**，确认态还会说明"名字不是完全一致"
- 结果按名字缓存在进程内，同一个模组只解析一次

实测命中率与耗时：

| 模组 | 词条 | 耗时 |
|---|---|---|
| Fabric API | `class/3124` FabricAPI | 0.8s |
| Sodium | `class/2785` 钠 (Sodium) | 0.8s |
| Create | `class/2021` 机械动力 (Create) | 1.0s |
| OptiFine | `class/36` [OF] 高清修复 | 0.8s |
| Iris Shaders | `class/3697` IrisShaders | 1.8s |
| Mod Menu | `class/1675` 模组菜单 (ModMenu) | 2.0s |

（`JEI` 这种**缩写**对不上是合理的——百科词条叫 "Just Enough Items"，
它会退回搜索页。**拿不准宁可不跳**，跳错词条比让用户多点一下糟糕得多。）

## 六、加载行为（这版改过，值得知道）

### 分批加载

| | 每批 | 触发 |
|---|---|---|
| 搜索页 | 12 条 | 拖到底加载下一批 |
| 详情页 | 12 个版本分组 | 拖到底建下一批 |

- **是"拖到底"才加载，不是提前预加载**（阈值只留了几十像素余量，避免贴底那一瞬间空白）。
- **首批仍会多补一批**：12 张卡片填不满一屏时（视口高的话），会自动再补一批填满，否则首屏下半部分是空白。这个"自动补"最多连续 1 次。
  想严格只给 12 条：把两个页面里的 `MAX_AUTO_FILL` 改成 `0`。
- 内容不够一屏、滚动条拉不动时，会出现「加载更多」按钮兜底。

### 按帧预算建造（治"卡一下下"）

数据到达时**不是一口气把所有卡片造出来**，而是每帧最多干 12ms / 最多造 6 张，剩下的下一帧接着来。

为什么：实测一口气造 24 张要 **39ms**，而一帧预算只有 **16.7ms**——主线程被独占，界面冻住，看着就是"顿一下再一股脑出来"。

可调参数（两个页面文件顶部）：

```python
FRAME_BUDGET_MS = 12.0   # 每帧最多花多少毫秒
FRAME_MAX_ITEMS = 6      # 每帧最多造几张
```

机器更慢就把 `FRAME_MAX_ITEMS` 调到 3~4；想更快出画面就调大。

## 七、下载窗口（独立窗口）

点版本卡片上的「下载」不再原地等，而是弹出**独立的非模态窗口** —— 下着的时候还能继续翻版本列表、点别的 mod。

### 窗口里有什么

| 位置 | 内容 |
|---|---|
| 标题 | `下载任务` + 副标题（`正在下载 3 个文件…` / 收尾后 `完成 5 个`） |
| 总进度条 | 整批任务的总百分比；有文件大小未知时退化显示已下字节数 |
| 左列读数 | 总进度 / 下载速度 / 剩余文件 |
| 右侧列表 | 每个文件一行：`[类型] 名字` + 进度条 + 状态（等待中/下载中/完成/失败/已取消） |
| 底部 | 保存到哪 |
| 右下角 | `取消下载` / `关闭` |

版式走 HMCL 那一路（读数在左、列表在右），内容项照 PCL2 的「任务管理」取（进度 / 剩余文件 / 速度 / 文件名）—— 但**没有照搬任何一边**。列表是能装的：整合包那种几百个文件也是同一套行。

### 速度怎么算的

**滑动窗口**，不是"总字节 ÷ 总耗时"。后者会把早期的慢速一直平均进去，速度掉下来半天回不去。

`core/download.py` 里每个任务记最近 `SPEED_WINDOW = 2.0` 秒的采样，超时的丢掉；窗口里样本不够时退回"已下 ÷ 已用时间"。

### 取消是干净的

取消 → worker 下一次循环检查时停下 → 删掉 `.part` → 退出。

**不会留半个文件**：全程写 `xxx.jar.part`，收完才 `temp.replace(path)`（同目录改名，原子操作）。所以 mods 目录里不会出现"下了一半的 jar 被游戏加载"这种事。

### 为什么用定时器刷，不用信号

下载线程每收 64KB 就发一次信号 —— 10MB 的文件就是 160 次，再乘并发数，每次重建一堆 QLabel 文本纯属浪费。这里统一走 `REFRESH_MS = 150` 的定时器（人眼看不出差别），线程那边只管累加字节数。

定时器里还有第二层：**值没变的行直接跳过**。实测 40 行全量刷 `0.077ms`/轮，跳过未变的只要 `0.009ms`（省 88%）；折算到 500 个文件，全刷约 1ms、跳过约 0.12ms，每 150ms 一次。

### 以后真要下整合包（几百个文件）

现在是"一个文件一个 `_TaskRow`"（`QFrame` + 2 个 `QLabel` + `QProgressBar`）。500 个文件就是 500 个常驻控件，滚动和布局会开始有压力。那时候该换成 `QListView` + 自定义 delegate（只渲染看得见的行）。

**当前没做** —— 一次最多几十个文件，没必要提前上复杂度。

### 下到哪：游戏目录 → 版本文件夹

点「下载」后的落点是**算出来的**，不是写死 `<游戏目录>/mods`：

```
<游戏目录>/versions/<版本文件夹>/<mods | shaderpacks | resourcepacks | datapacks>/
```

`<版本文件夹>` 由用户**点的那一版**决定：在「Fabric 1.20.4」这一组里点下载，
就去找 `versions/1.20.4-Fabric 0.19.5/`。这是**版本隔离**的安装 ——
mods 在版本文件夹里，`.minecraft/mods` 那份是空的甚至没有。

命名是启动器们的约定（这台机器上实测就是这样）：

| 文件夹名 | 含义 |
|---|---|
| `1.20.4` | 原版，就一个游戏版本号 |
| `1.20.4-Fabric 0.19.5` | Fabric，**空格**分隔 loader 版本 |
| `1.12.2-Forge_14.23.5.2864` | Forge，**下划线**分隔（两套都有，别只认一种） |

匹配规则（`core/mc_dir.py`）：`-` 前面必须**等于**游戏版本，`-` 后面必须以加载器名
**开头**。用"开头"而不是"包含"是有原因的 —— `forge` 包含在 `neoforge` 里，
用包含会让装 NeoForge 的用户把 Forge 版下进 NeoForge 的文件夹。
同一个游戏版本装了好几份（Loader 版本不同）就取版本号最高的那个。

匹配不上退回 `<游戏目录>/mods`，并在确认框里写明原因；再没有就明确提示去设游戏目录。

确认之后弹「另存为」，**预填到算好的位置**（文件名就是 mod 的文件名），想换地方还能改。

### 游戏目录是怎么定的

优先用设置里存的那个（工具栏「背景」→「游戏目录」→「浏览」，选到 `.minecraft` 那一层；
选进 `versions/` 或某个版本文件夹里也会自动往上纠）。没设过就自动探测。

探测**不是**"`%APPDATA%/.minecraft` 存在就用它" —— 这台机器上有 **6 份** `.minecraft`：

| 目录 | 版本数 | 最近玩过 |
|---|---|---|
| `C:\…\AppData\Roaming\.minecraft` | 3（只有原版） | 09-18 |
| `D:\DHML\.minecraft` | 11（Fabric / Forge） | **09-24 14:31** ← 真正在用的 |
| `D:\MINECRAFT\.minecraft` | 52（Fabric / NeoForge / Forge） | 09-24 05:11 |
| `D:\MTR 4.0\.minecraft` | 2 | 04-26 |
| `D:\Xinghai City4.9.0\.minecraft` | 1 | 04-25 |
| `E:\game\.minecraft` | 16 | 03-03 |

所以按 `(有没有装加载器, 最近游玩时间)` 排序挑。最近游玩时间取
`versions/*/logs/latest.log` 的修改时间（每次启动游戏都会重写），没有就退回
`options.txt`、再退回版本文件夹本身。

⚠️ 只看"版本最多"会挑错：`D:\MINECRAFT` 有 52 个版本，比真正在用的
`D:\DHML`（11 个）多得多。必须要有"最近被用过"这个信号。

探测结果**不写进配置** —— 换机器、插移动硬盘时不该被固化；想固定就用「浏览」选一次。

## 八、踩过的坑（改这块代码前先看）

### 1. 主线程联网 = 卡死

**详情卡图标原来是同步下载的**（`requests.get(icon_url, timeout=10)` 跑在主线程），实测点进详情页卡 **2.4 秒**。已改成异步（线程池 + 磁盘缓存）。

**规矩：任何 `requests.get` 都不许出现在主线程路径上。** 搜索、图标、详情数据全走 `QThread` / `QRunnable`。

### 2. 卡片包一层 SlideInRow 后，`sizeHint()` 量不到高度

折叠分组的展开高度如果直接读 `content.sizeHint()`，会把隐藏的卡片行算成 0——展开后看不到内容，表现成"点了没反应，下载按钮出不来"。

解法：**自己逐行累加**（见 `collapsible_group._expanded_height()`），不依赖布局对隐藏控件的态度。

### 3. 两条并行动画不能写同一个属性

PCL 那种"位移拆两条曲线"必须用**两个独立属性**（`fastOffset` / `slowOffset`）再合成。两条 `QPropertyAnimation` 同时写一个属性，Qt 这边会打架：位移卡在起手值不动、父组状态报 Stopped 但里面还在跑。

（WPF 能容忍这个，Qt 不能。）

### 4. Qt 最多只支持 10 个自定义缓动函数

`pcl_ease.named()` 必须缓存曲线；超了会抛 `a maximum of 10 different easing functions are supported`。

### 5. 给 QPushButton 套样式表后它会横向撑开

类型标签按钮当初被拉得铺满整个面板宽度，`QSizePolicy.Fixed` 都压不住。解法：行末加 `addStretch(1)` + 给按钮设 `setMinimumWidth(92)` 让它们等宽。

### 6. `QStackedWidget` 会盖住背景图

背景是自己画的（`BackgroundCanvas`），但 `QStackedWidget` 和页面默认会用调色板 window 色**不透明地填满**自己，把背景整个盖掉（实测设红色图只显示深灰）。解法：主窗口样式表里让它们透明：

```css
QStackedWidget { background: transparent; }
QStackedWidget > QWidget { background: transparent; }
```

### 7. `setGraphicsEffect` 要记得摘

淡入用的 `QGraphicsOpacityEffect` 在动画结束后必须 `setGraphicsEffect(None)`，否则每帧都走离屏合成，白白拖慢滚动。

### 8. 模态框在离屏测试里会卡死

写自动化测试时，`QMessageBox` / `QFileDialog` 弹出来没人点，脚本就永远停在那儿。测试里要先打桩：

```python
QMessageBox.question = staticmethod(lambda *a, **k: QMessageBox.StandardButton.Yes)
QFileDialog.getExistingDirectory = staticmethod(lambda *a, **k: "C:/tmp")
```

### 9. 可收起区块要自己管住高度

`CollapsibleSection` 放进紧凑布局（比如设置对话框）后，**内容会被挤扁**：量出来 73px、实际只渲染成 47px，展开动画看着"没展开完"。

原因：`QWidget` 默认竖向尺寸策略是 `Preferred`，会跟着外部布局被拉伸/压缩。解法两处一起：

- `setSizePolicy(Preferred, Fixed)` —— 声明"我的高度我自己定"
- 每次状态变化都 `setFixedHeight(标题栏 + 间距 + 内容高度)`，并且**动画过程中逐帧同步**（不然内容会被自己的边界裁掉，看着像被"切"）

还有个反直觉的点：展开动画结束后**不能**把 `maximumHeight` 放开成无限大——放开之后外层布局会把内容拉伸到剩余空间（实测 132 → 331），动画最后一下会"弹"。

### 10. 收起时"标签和字会闪" —— 因为动画期间内容还在重排

原来的收起是把内容的 `maximumHeight` 从 306 压到 0。副作用：**内容自己的高度每帧都在变**，
于是里面每个子控件（版本卡片、标签、文字）每帧都被重新摆一遍 —— 看着就是文字在抖/闪。

修法是改成**裁剪式**（`ui/widgets/clip_box.py`）：

```
本控件高度  ---------> 0     （外层布局看到它在收，跟着收）
内容高度    一直 = 306        （子控件一动不动，不重排）
```

关键点：

- 裁剪用 **Qt 原生的**：父控件 `paintEvent` 里设的 `setClipRect` **会作用到子控件**，
  不需要手动 `render` 每个子控件（早期版本那么写过，又慢又容易错）
- 本控件高度必须**自己咬死**（`setFixedHeight`）：挂进布局后会被拉伸（实测内容 306 被拉到 737）
- 内容高度**用逐行累加算**，别用 `sizeHint`：卡片还没滑入时 sizeHint 偏小，
  会导致最后一行被裁掉 1px
- 窗口宽度变化时要**重算**高度（文字换行会让行数变）—— 在 `resizeEvent` 里做，
  但要跳过动画进行中的情况

验收标准很简单：**收起/展开期间，内容高度应该只有一个取值**。测试里就是这么断言的。

### 11. 详情页的竞态：上一个 mod 的结果会盖掉新的

**现象**：点进 Fabric API，返回，再点 Sodium —— 界面显示的却是 **Fabric API**
（图标、标题、版本列表全是旧的），而且底部加载条还在转。

**原因**：`_on_loaded` 里**没有校验"这个结果是不是当前这个 mod 的"**。

```
点 Fabric API  → 起线程 A（要打两次 HTTP，1~3 秒）
快速返回、点 Sodium → 起线程 B
B 先回来 → 界面显示 Sodium        ← 正常
A 晚回来 → 覆盖成 Fabric API      ← bug
```

慢的那个赢，因为它是最后写界面的。

**修法**：请求令牌。每次 `load()` 递增 `self._load_token`，回调里核对：

```python
def load(self, mod_id):
    self._load_token += 1
    token = self._load_token
    loader = ProjectLoader(mod_id)
    loader.loaded.connect(lambda p, v, t=token: self._on_loaded(p, v, t))
    ...

def _on_loaded(self, project, versions, token=None):
    if token != self._load_token:
        return          # 过期结果，直接丢
```

几个要点：

- **别用 mod_id 当令牌**：用户可能连点同一个 mod 两次，那样两次的令牌一样，防护就失效了
- **失败提示也要挡**：过期请求的 `failed` 不该弹"未找到"框（会盖掉新 mod 的正常界面）
- **图标同样要挡**：详情卡是**复用同一个控件**的，迟到的图标会把新 mod 的图标盖掉。
  原来用 `_mcmod_name` 判图标归属是错的（那是给百科按钮用的字段），现在统一用
  `_icon_token`
- 顺手加了：换 mod 时把版本列表**滚回顶部**（沿用上一个的滚动位置会让人以为没加载）

实测：用过期令牌送 Fabric API 的结果 → 卡片纹丝不动；用当前令牌送 Sodium → 正常显示。

### 12. 绕过 stagger 直接建行 → 整个动画静默失效

**这是我改"卡顿"时引进来的回归**，而且藏得深：

原来加密错动画是这么写的：

```python
row = self.stagger.add(card)      # ← 交给调度器排队
self.results_layout.addWidget(row)
```

后来为了修"数据到达时一口气造 24 张卡"的卡顿，改成了按帧预算建造，
顺手写成：

```python
row = SlideInRow(card, ...)       # ← 自己 new，绕过了调度器
self.results_layout.addWidget(row)
```

**`stagger.start()` 于是什么都不做** —— 队列是空的。卡片就永远停在
**起手位置**（偏移 = offset = 120px，被推出可视区外面）。

看起来像"列表是空的"，或者"切换时显示的还是上一个页面的东西"
（其实两张卡片都在屏外，只有旧内容残留可见）。而且它**不报错**，
测试只看"卡片数量对不对"的话完全发现不了。

**判据**：`stagger.add()` 的返回值才是登记过的行。自己 new 出来的行，
要么交给 `add()` 排（推荐），要么就自己管播放。

**这类问题的通用检查**：动画"没反应"时，先看**队列长度**
（`stagger.pending_count()`）和**行的偏移值**，别只看控件数量。

### 13. `clear()` 不能把"已就位"的行推回起手位置

修上面那个问题时，`clear()` 里加了"把已出场（包括已播完）的行也停掉"。
但当时的 `stop()` 写的是「重置到起手位置」，于是**已经就位的卡片被推回屏幕外**：

```
搜索页 12 张卡片全部卡在偏移 120 → 整个列表看不见
```

`stop()` 的语义应该是**停动画 + 归零（就位）**，不是回到起点：

```python
def stop(self):
    self.anim.stop()
    self._fast_offset = 0.0
    self._slow_offset = 0.0
    self._apply(0)                 # 归零 = 就位，不是 self._offset
```

**验收标准**：任何一次列表刷新之后，所有行的偏移都应该是 0。
测试里就是这么断言的（`all(r._slide_offset == 0 for r in rows)`）。

### 14. "URL 没变就跳过请求"这个优化会饿死图标

详情卡加了**预填**（点卡片的瞬间先用搜索结果填上名字/图标/描述）之后，
图标变成了空白 `?`。原因是一个自作聪明的优化链：

```python
# prefetch() 里已经发过图标请求，并把 _icon_url 设成了这个 URL
# 然后正式 load() 进来：
self._icon_token += 1                        # ← 把预填那次的结果作废了
if icon_url != self._icon_url:               # ← URL 没变，于是跳过
    self._load_icon_async(icon_url)          # ← 结果再也没人去取图标
```

**作废了旧的 + 跳过了新的 = 谁都不干**。

修法：`load()` 里图标**每次都重新走一遍**（第一步就查磁盘缓存，重复调用几乎零成本）：

```python
self._icon_url = ""
self._load_icon_async(data.get("icon_url", ""))
```

教训：异步请求的"去重优化"必须和"结果归属校验"配套想清楚 ——
凡是靠令牌作废旧结果的地方，都要保证**新的那次一定会发出去**。

### 15. 重复进入同一个页面：列表翻倍 + 切页掉帧

**① 列表翻倍**。修"加载出来后列表又没了"时，我给 `load()` 加了
"同一个 mod 就不清列表"（免得闪空），但 `_on_loaded` 里没有对应的清理 ——
新分组**追加**在旧的后面，每次进入分组数就翻倍（12 → 24 → 48）。

**"保留旧的"和"替换成新的"必须配对**：旧的留到新数据回来那一刻，
重建前丢掉一次：

```python
def _on_loaded(self, ...):
    ...
    self._clear_group_list()      # ← 重建前清一次
    self._load_many_groups()
```

**② 切页掉帧**。整页横向滑动是"每帧重画整个页面"的场景，最吃渲染
（实测帧间隔被拉到 40~70ms，看着就是抖）。做法是**动画期间关掉重绘**：

```python
page.setUpdatesEnabled(False)     # 动画开始前
anim.start()
# 结束时（finished 回调里）一定要打开，否则页面再也不刷新
page.setUpdatesEnabled(True)
page.update()
```

改完帧间隔中位 **1.6ms**、p95 3ms（原来 40~70ms）。

顺带把页面切换动画统一到 `_slide_page()` 一个入口，顺手解决了
"上一条动画没播完就又切页"的问题（先 `stop()` 再建新的）。



**这类 bug 的通病**：异步 + 复用控件 + 没有归属校验。项目里凡是"异步结果写界面"的地方，
都该有一个令牌（`detail_page._load_token`、`detail_card._icon_token`、百科解析的
`_mcmod_name` 都是这个套路）。

### 16. 别信"我模拟出来了" —— 测试脚手架本身会骗人
排查上面那个竞态时，我连着写了 4 版模拟测试，**4 版都没真正复现**：

- 用真实网络"碰运气"：两次都超时，什么也没证明
- 把令牌归零想模拟"修复前"：结果**所有**结果都被丢弃，反而更糟
- 把 `_on_loaded` 包一层：参数传的是当前令牌，照样通过校验，等于没绕过
- 用 `QTimer.singleShot` 造"慢的那个"：**它的定时器根本没触发**（日志里只有快的那个）

最后靠**直接调用 `_on_loaded(数据, 过期令牌)`** 才把逻辑验清楚。

教训：验证一个"时序 bug"的修复时，**别去费劲复现竞态，直接验证判定逻辑**
（"过期的东西会不会被应用"），前者容易假阴假阳，后者是确定的。

**补充一条（2026-09 又踩）**：离屏测试里的 `app.processEvents()` **不会处理
`DeferredDelete` 事件**，所以 `deleteLater()` 的控件永远不销毁。连着改几轮结果数
再量几何，量到的是"新旧混在一起"的假象（当时表现成"12 条时行高变成 89/90"）。
真实程序有事件循环，会正常回收。测试里要显式补上：

```python
app.processEvents()
app.sendPostedEvents(None, QEvent.Type.DeferredDelete)
```

还有两个同类的坑：**分批揭示动画没放完就量**（40 张卡片每 95ms 放一张，全放完要 4 秒，
中途量到的行数偏少）、**布局还没结算就量**（最后一张刚出现的那一帧，容器高度还没更新完）。
量之前先 `wait_until(条件成立)` 再 `pump(0.5)` 等布局稳定。

### 17. 数据类不能直接当字典的键

`DownloadTask` 是 `@dataclass`。默认 `eq=True` 会生成 `__eq__` 并把 `__hash__` 置成 `None`
—— 拿它当 `dict` 的键（worker 表是 `{task: worker}`）当场炸：

```
TypeError: cannot use 'core.download.DownloadTask' as a dict key
```

修法：`@dataclass(eq=False)` —— 按对象身份比较、可哈希。
（`frozen=True` 也能哈希，但任务状态是要中途改的，用不了。）

### 18. "取消"标志是粘的

`DownloadManager` 用一个 `threading.Event` 广播取消。第一版只在 `_cancel is None`
时才创建它 —— 用户点过一次「取消下载」之后，这个事件**永远处于置位状态**，
后面排队的新任务会被 worker 立刻判定成"已取消"，**一个都下不动**。

修法：`start()` 里发现事件已置位就**换一个新的**。

验收：取消一批 → 再排一批 → 必须有文件真的下完（实测 4/4 完成）。

### 19. 取消是异步的，关窗前必须等线程退出

`cancel_all()` 只是置位标志；worker 得写完手头那块 64KB、删掉 `.part` 才会返回。
窗口紧接着被销毁的话，QThread 就在"还在运行"的状态下被析构：

```
QThread: Destroyed while thread is still running
```

修法：`DownloadManager.wait_all(timeout_ms)`（内部对每个 worker `wait()`），
关窗确认后调一次。实测 4 个进行中的任务，`close()` 383ms 返回，
worker 残留 0、`.part` 残留 0。等待有上限，不会把界面永久卡死。

### 20. 定时刷新里别再调自己

`_refresh()` 判到"全部完成"时顺手又调了一次 `_refresh()` 想清掉速度值 ——
无限递归，直接 `RecursionError`。

不用调：这次调用本来就会把后面的代码走完，只需要 `self._timer.stop()`。

### 21. 滚动区不设样式会露白底

`QScrollArea` 和它的 viewport 带系统默认的浅色底，在深色窗口里就是一大块刺眼的灰。
必须**显式给滚动区和它的内容控件都设透明**：

```python
QScrollArea, QScrollArea > QWidget > QWidget {
    border: none; background: transparent;
}
```

只写 `QScrollArea { background: transparent; }` **不够** —— viewport 那一层还是浅的。

### 22. `except Exception` 吞掉 ImportError → 功能静默失效

详情页原来写的是：

```python
default_dir = Path(self._mc_dir()) / "mods"
```

而 `_mc_dir()` 里是 `from core.config import config` —— 这个实验项目的 `core/` 里
**根本没有 config.py**（那是主项目的）。ImportError 被 `except Exception: return Path.home()`
接住，于是"默认落到游戏目录"**从来没生效过**：每次点下载，文件夹对话框都在
用户主目录里开。而注释还写着"默认落到 <游戏目录>/mods"，看着一切正常。

教训：**兜底回退要能被看见**。这种"拿不到就用默认值"的写法，错了也不报错，
只表现成"位置有点怪"，能藏很久。写回退的时候顺手 `print` 一句也好。

### 23. 别用"包含"匹配加载器名

`"forge" in "1.20.4-neoforge 20.4"` 是 **True**。用包含的话，
装 NeoForge 的用户点 Forge 的版本会下进 NeoForge 那个文件夹。必须 `startswith`。

顺带：版本文件夹名里 loader 版本的分隔符**两套都有** ——
`Fabric 0.19.5`（空格）和 `Forge_14.23.5.2864`（下划线）。只按一种解析会漏掉另一半。

### 24. 同一台机器上可能有好几份 .minecraft

实测 6 份（见第七节）。自动探测按"第一个存在的"或"版本最多的"挑都会挑错。
最后靠 `versions/*/logs/latest.log` 的修改时间（= 最近启动过游戏）才分开。

教训：**有多个同类候选时，要找"最近被用过"的信号**，别只看体量。

### 25. 建目录失败要中止，不能硬着头皮下

`target.mkdir()` 可能失败（权限、盘符掉线、路径太长）。
失败了必须**警告并中止**，否则下载线程会在一个不存在的目录里写 `.part`，
最后报一个和真实原因八竿子打不着的错。

（这条是测试里真踩出来的：沙箱不让在 `D:\DHML\.minecraft` 里新建 `shaderpacks`，
`mkdir` 抛 OSError —— 幸好走了警告分支，而不是继续往下跑。）

### 26. 列表末尾的"撑开项"不能省，卡片也不能跑到它后面

**现象**：搜索结果少的时候，卡片之间隔一大段空白。实测 2 条结果时**每行被拉到 224px**
（卡片本身 `setFixedHeight(100)` 没变），多出来的 124px 就是那段空白。

**为什么会这样**：`QScrollArea` 开了 `setWidgetResizable(True)`，内容不满一屏时
容器会被撑到视口那么高。多出来的高度要有地方去 —— 布局末尾没有撑开项的话，
`QVBoxLayout` 就把它**平摊给每一行**。

而撑开项确实"丢了"，两个原因叠在一起：

```python
def _clear_results(self):
    while self.results_layout.count():
        item = self.results_layout.takeAt(0)   # ← spacer 也被摘掉了
        w = item.widget()
        if w:
            w.deleteLater()                     # spacer 没有 widget()，看着像没碰它
```

`addStretch()` 建的 spacer **没有 `widget()`**，所以那个循环看起来"只删控件、
不动 spacer"，实际上 `takeAt` 已经把它从布局里移除了。

**光把 `addStretch()` 加回来还不够**：它是布局里的一个普通项，之后 `addWidget()`
追加的卡片会跑到它**后面**去（代码里原来那句注释"加了 stretch 之后卡片会跑到
stretch 下面"说的就是这个现象 —— 但当时的结论是"那就不加 stretch"，于是踩了另一个坑）。

正确做法是两条一起：

```python
# 1) 撑开项常驻，清空后补回来
self.results_layout.addStretch()

# 2) 卡片插在它**前面**
self.results_layout.insertWidget(self.results_layout.count() - 1, w)
```

**第三层保险**：`SlideInRow` 的垂直 size policy 设成 `Fixed`
（`QSizePolicy.Policy.Preferred, QSizePolicy.Policy.Fixed`）——
一行的高度永远等于它包着的内容，从根上不让它吃多余空间。

**验收**：任何结果数下，行高恒为 100、相邻间距恒为 8、首行 y=2、
容器高 = `max(视口高, 内容高)`，且布局里**有且只有一个**撑开项。

### 27. 没进布局的控件会变成一个独立窗口

`_show_more_btn()` 原来是：

```python
self._more_btn = self._make_more_btn()   # QPushButton("加载更多")，没给 parent
self._more_btn.setVisible(True)          # 就这样"显示"了
```

既没有父控件、也没进任何布局 → 它是个**顶层窗口**，会飘在桌面上。
只有"内容不够一屏"时才会走到这里，所以不容易撞见。

**规矩：动态创建的控件，要么构造时给 parent，要么立刻加进布局。**

## 十、已知限制

- **正版/第三方验证没做**，只有离线账户概念（这个实验项目里连账户 UI 都没有）。
- **下载没有断点续传**，中途失败要重来。
- **下载窗口只能整批取消**，没有"暂停/恢复"和单文件取消。
- **下载窗口的文件列表每行一个真控件**。几百个文件的整合包建议换成 `QListView` + delegate（见第七节末）。
- **落点只认"版本隔离"的目录结构**（`versions/<版本>/mods`）。非隔离的安装靠"匹配不上就退回 `<游戏目录>/mods`"兼容，但"哪个 mod 属于哪个版本"这类判断没做，也不会去读已装 mod 的清单。
- **版本分组会全量获取**：Fabric API 有 1203 个版本，接口一次返回全部，然后本地分组（`group_versions()` 只要 9ms，不是瓶颈）。真要优化得看 Modrinth 支不支持分页。
- **动画顺不顺最终受渲染后端影响**。如果连"详情页从右滑入"这种整页动画都卡，那是 Qt 的渲染后端问题（软件渲染 vs GPU），跟这套动画代码无关。
